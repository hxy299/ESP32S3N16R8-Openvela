# 连接失败：中心设备侧退避的假设（2026-10-11 第六轮）

> 本文提出一个**新的、很可能的解释**，并给出验证方法。

---

## 一、新假设：中心设备（手机）对板子做了退避/黑名单

### 1.1 现象回顾

| 观察者 | 现象 |
| --- | --- |
| Windows（bleak） | 扫到 `BTSH-LIGHT`（RSSI −16），**连接超时 46 秒**，板子串口 `le_conn_complete` = 0 |
| 手机系统蓝牙 | **能看到** `BTSH-LIGHT`（用户确认） |
| 手机 nRF Connect | **扫不到** |
| 手机（用户操作） | **点了没反应 / 设备从列表里消失** |

### 1.2 为什么怀疑退避机制

**关键历史**：在 `BT_GATT_CCC` bug 未修复时（见 [`HT-11`](../../tests/hardware/HT-11-ble-connect-crash.md)）：

> **手机一连上，板子就崩溃复位**（`rst:0x13`，每 2 秒一轮死循环）

即：**这台手机曾经反复经历"连接 → 设备崩溃消失"**。

**Android 蓝牙栈对此类设备有退避行为**：
- 记录连接失败的设备
- 在一段时间内**不再主动尝试**，甚至从扫描列表里隐藏
- 系统蓝牙列表可能仍显示（缓存的已配对/已见设备），但实际连接不再发起

**这与观察完全吻合**：
- ✅ 系统蓝牙能显示（缓存）
- ❌ nRF Connect 扫不到（被过滤）
- ❌ 点了没反应（不真正发起连接）
- ✅ Windows 是**另一台主机**，没有这段历史 —— 但它也连不上（见 §3）

### 1.3 ⚠️ 但这个假设有反证

**Windows 从未参与过 CCC 崩溃时期的连接**，却同样连不上
（`le_conn_complete` = 0，超时 46 秒）。

**所以退避假设只能解释"手机"这一侧，不能解释 Windows 侧。**

两个问题可能**并存**：
1. 手机侧：对板子退避（导致扫不到/点了没反应）
2. 板子侧：控制器不响应连接（导致 Windows 也连不上）

**或者**：Windows 侧我用的 bleak 库本身有问题（从未验证过它能连**任何** BLE 设备）。

## 二、如何验证退避假设

### 方法 A（最快）：换另一台手机（或另一台电脑）测试

另一台设备没有"失败记忆"，能立刻看出板子是否正常。

**判读**：

| 结果 | 含义 |
| --- | --- |
| 新手机能扫到并连上 | **板子正常**，原手机有退避记录 |
| 新手机也连不上 | 板子侧确实有问题（控制器/ACL） |

### 方法 B：改掉板子的 BLE 地址

手机就会当成**全新设备**，不套用旧的退避记录。

**当前状态**：NuttX **没有** `LE Set Random Address` 的支持
（`grep -rn "LE_SET_RANDOM_ADDR" wireless/bluetooth/*.c` 结果为空）。

**实现路径**：
1. 在 `bt_hci_core` 里加 `bt_set_random_address()`，调用
   `BT_HCI_OP_LE_SET_RANDOM_ADDR`
2. 把 `set_param->own_addr_type` 从 0（公共）改为 **1（随机）**
   （位置：`bt_hcicore.c:2145-2149`，当前 `memset` 后未显式设置）
3. 应用启动时先设随机地址、再广播

**代价**：需要改 NuttX 内核代码（约 40 行），但可控。

### 方法 C：清除手机蓝牙缓存

设置 → 应用 → 蓝牙 → 存储 → 清除缓存（部分机型需清除"数据"）
或直接重启手机。

## 三、板子侧仍待解决的问题

**无论在多少台中央设备上测试，板子串口始终 `le_conn_complete` = 0**
（Windows 三次、手机多次）。

### 3.1 已确认正常的部分

| 项 | 状态 | 证据 |
| --- | --- | --- |
| 控制器初始化 | ✅ | `bt bnep0 info` 读到 BDAddr |
| 扫描 | ✅ | 发现 21 个真实设备，含完整 advertiser data |
| 广播参数 | ✅ | 间隔 187.5 ms、三信道、`BT_LE_ADV_IND` |
| 广播数据 | ✅ | 名字 `BTSH-LIGHT` 完整（本轮修复后），RSSI −16 |
| 被其他主机发现 | ✅ | Windows bleak 能扫到 |

### 3.2 未解决的核心问题

> **控制器收到 `CONNECT_IND` 后不产生 `LE Connection Complete` 事件。**

### 3.3 历史反证（重要）

`HT-11` 记录中，**手机上曾成功建立 3 次连接**：

```
>> 连接: le_conn_complete: status 0 handle 1 role 1 7C:53:C7:63:31:64 (random)
[ 60s] 复位=0 连接=1 GATT=1
[ 90s] 复位=0 连接=2 GATT=2
[120s] 复位=0 连接=3 GATT=3
```

**说明控制器能够响应连接请求。** 只是那次的 ACL 数据不通。

**注意 `(random)`**：那三次连接的对端是**随机地址**。
而当前广播用**公共地址**（`own_addr_type = 0`）。

> 📌 这为"方法 B（改用随机地址）"提供了额外动机 ——
> 也许改用随机地址能同时绕开中心设备的退避过滤。

## 六、诚实评估

**我目前无法确定连接失败的根本原因。** 已排除 30+ 项，
剩下的可能性集中在：

| 可能 | 验证方式 |
| --- | --- |
| 中心设备侧退避（手机） | 换手机 |
| 中心设备侧工具问题（Windows bleak） | 用手机代替 |
| 公共地址不被某些中心接受 | 改用随机地址 |
| 控制器/ACL 层缺陷（NuttX ESP32-S3 适配） | 需要蓝牙嗅探器或逻辑分析仪观察空口 |

**若要继续深入，建议的硬件手段**：
- **蓝牙嗅探器**（如 Nordic Sniffer / Ubertooth）：直接看空口上 `CONNECT_IND`
  是否发出、控制器是否回了数据
- **逻辑分析仪**：看控制器与主机之间的 VHCI 信号

**替代路线**：WiFi/TCP 已验证可用（见 [`stage-05`](stage-05-tcp-remote-light.md)）。
